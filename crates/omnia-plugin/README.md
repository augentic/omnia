# omnia-plugin

The `omnia:plugins/loader` capability for the [omnia](https://github.com/augentic/omnia) runtime — the guest loader. A caller names a location — `declared(name)`, one of the deployment's `[[guest]]` entries; `path(p)`, a component beneath one of its read-only mounts; `registry(package, endpoint?)`, an exact package — with an optional digest, and the host acquires the bytes inside the deployment's grant, verifies them against the digest, and admits them through the runtime's admission seam under the name the location derives: the declared name, the path's file stem, or the package reference without its version. Component bytes never cross the interface, and nothing a caller passes widens the grant: a `declared` name outside the deployment's guest list is refused, one not yet loaded goes through the runtime's own first-use seam (`Runtime::guest`, the same one a route or a link call loads it through), an active one is attested, not fetched, and a path or package that would register under a declared name is refused whether or not that guest has loaded, the name being its entry's alone; a `path` loads through the read-only mount it lies beneath alone — a writable mount is refused before the file is read, and a writable mount overlapping a read-only mount's directory, by identity rather than path, is refused at assembly; a `registry` package is served from the deployment's package store when it holds the release, else fetched by the routing the deployment's `registries` declares — the load's `endpoint` serving only a namespace it routes nowhere — and written to the store once. A path or package the caller names admits raw wasm alone; a declared `source.path` admits a pre-compiled artifact only when its entry pins the `digest` (read while guests run, an unpinned file is refused), and a declared `source.package` admits raw wasm alone.

Everything loader lives here:

- the loader WIT and the `WasiPlugins` host binding,
- the `Plugins` load path (location resolution, idempotency): a `declared` name through `Runtime::guest`; a caller-named path read through the mount it lies beneath, a caller-named package fetched through `Runtime::acquire`, each admitted through `omnia-core`'s one admission body, `Runtime::admit_bytes` under `Policy::CallerNamed` — the pin check, `Verified::wasm`, and the rule that a declared name is its entry's alone live there, for the loader and `Runtime::register` alike — reachable host-side through `PluginLoader` on `Runtime`,
- the grant `Plugins::install` fixes: the runtime's mounts as path roots; and the `RegistryClient` the runtime acquires every package through — the default `RegistrySource` (a trait of `omnia-core`, through which the runtime also acquires a `source.package` guest at first use), store first: a `PackageStore` keyed by exact `Reference` (`FsStore`, a flat directory of `namespace_name@version.wasm` files, over the deployment's `plugins.store`; `NoStore` without one) answers before any registry, and a release it lacks is fetched by the deployment's `registries` configuration (the `runtime!` macro's `plugins: { store, registries }`, a manifest's `[plugins]`), verified, and written to the store once — one fetched from the `endpoint` a load names, for a namespace the configuration routes nowhere, is served to that load and never stored; `Deployment::assemble` installs both, and `Deployment::registry_source` selects a custom acquirer (a `RegistryClient` over a store of your own, say) before assembly.

Depend on the `omnia` facade, not on this crate: the whole surface re-exports there behind `omnia`'s non-default `loader` feature (`omnia::WasiPlugins`, `omnia::Plugins`, `omnia::RegistryClient`, …), including the trait a store of your own implements — `omnia::PackageStore` from here, with `omnia::FsStore`, `omnia::NoStore`, and `omnia::Reference` beside it — and `omnia::Backend` and `omnia::NoOptions` from the runtime core. A direct dependency on `omnia-plugin` (or on `omnia-core`) is only for building another capability crate of your own.
