# omnia-plugin

The `omnia:plugins/loader` capability for the [omnia](https://github.com/augentic/omnia) runtime — the guest loader. A caller names a location — `declared(name)`, one of the deployment's `[[guest]]` entries; `path(p)`, a component beneath one of its read-only mounts; `registry(package, endpoint?)`, an exact package — with an optional digest, and the host acquires the bytes inside the deployment's grant, verifies them against the digest, and admits them through the runtime's admission seam under the name the location derives: the declared name, the path's file stem, or the package reference without its version. Component bytes never cross the interface, and nothing a caller passes widens the grant: a `declared` name outside the deployment's guest list is refused, one not yet loaded goes through the runtime's own first-use seam (`Runtime::guest`, the same one a route or a link call loads it through), an active one is attested, not fetched, and a path or package that would register under a declared name is refused whether or not that guest has loaded, the name being its entry's alone; a `path` loads through the read-only mount it lies beneath alone — a writable mount is refused before the file is read, and a writable mount overlapping a read-only mount's directory, by identity rather than path, is refused at assembly; a `registry` package is fetched by the routing the deployment's `registries` declares, the load's `endpoint` serving only a namespace it routes nowhere. A path or package the caller names admits raw wasm alone; a declared `source.path` admits a pre-compiled artifact only when its entry pins the `digest` (read while guests run, an unpinned file is refused), and a declared `source.package` admits raw wasm alone.

Everything loader lives here:

- the loader WIT and the `WasiPlugins` host binding,
- the `Plugins` load path (location resolution, digest pin, idempotency): a `declared` name through `Runtime::guest`; a caller-named path or package through the shared pin check and `Verified::wasm` into `omnia-core`'s privileged `Runtime::admit` seam, reachable host-side through `PluginLoader` on `Runtime`,
- the grant `Plugins::install` fixes: the runtime's mounts as path roots, and the `RegistryClient` — the default `RegistrySource` (a trait of `omnia-core`, through which the runtime also fetches a `source.package` guest at first use) routed by the deployment's `registries` configuration (the `runtime!` macro's `registries:`, a manifest's `[registries]`); `Deployment::assemble` installs it, and `Deployment::registry_source` selects a custom registry (a caching `RegistryClient::cached`, say) before assembly.

Depend on the `omnia` facade, not on this crate: the whole surface re-exports there behind `omnia`'s non-default `loader` feature (`omnia::WasiPlugins`, `omnia::Plugins`, `omnia::RegistryClient`, …), including the traits a store-backed `RegistryClient::cached` acquirer implements — `omnia::ContentStore` and `omnia::ReleaseStore` from here, `omnia::Backend` and `omnia::NoOptions` from the runtime core. A direct dependency on `omnia-plugin` (or on `omnia-core`) is only for building another capability crate of your own.
