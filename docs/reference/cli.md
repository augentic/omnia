# CLI Reference

A runtime binary generated by `omnia::runtime!` accepts the `run` and `compile` subcommands — unless it is a [direct command](runtime-macro.md#direct-commands-raw-argv-passthrough) (`mode: command` with a compiled-in deployment), which removes the host CLI entirely: such a binary has no subcommands and no `--manifest`/`OMNIA_MANIFEST` override, and forwards its argv to the command guest verbatim (`mybin greet Ada`, not `mybin run -- greet Ada`). It takes no `--env` either, so its guests see the host variables its [`env:`](runtime-macro.md#inline-manifest-keys-guests-mounts-env-plugins) key names. Everything below describes the standard grammar, which ships in the `omnia-cli` crate and reaches every binary through the `omnia` facade.

## `run`

Run a single guest, or a manifest-driven deployment.

```bash
<runtime> run [WASM] [--manifest <omnia.toml>] [--mount <spec>]... [--env <name>]... [-- <guest args>...]
```

| Argument / flag         | Meaning                                                                                                                                                                          |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WASM`                  | Path to a guest — a standard WASI component (`.wasm`) or a pre-compiled component (`.bin`). Optional when a manifest is available via `--manifest`, `OMNIA_MANIFEST`, or the binary's compiled-in default. |
| `-m, --manifest <path>` | Deployment manifest (`omnia.toml`) for multi-guest deployments. Falls back to the `OMNIA_MANIFEST` environment variable, then to a default manifest compiled in via the `runtime!` macro's `manifest:` field or inline manifest keys (if declared). |
| `--mount <spec>`        | Preopen a host directory into the guest sandbox (repeatable). Layered over the manifest's `[[mount]]` entries; a matching guest-visible name overrides the manifest (last wins). A guest that declares grants sees the mount only when its `mounts` grant names it. |
| `--env <name>`          | Pass a host environment variable to every guest (repeatable). A name ending in `*` passes every variable it prefixes, and `*` alone passes them all; quote a pattern so the shell does not expand it. Added to the `[env] inherit` of whichever manifest the run selects. A guest sees no host variable the run does not name, beyond the `RUST_LOG` and `NO_COLOR` the runtime sets, and a guest that declares grants sees only those its `env` grant names. |
| `-- <args>...`        | Everything after `--` is the command guest's argv (command mode). Its `wasi:cli/run` reads them after `args[0]`, the program name the runtime supplies. No other guest sees them, and a server refuses them. |

### Mount spec format

```text
path=<host-path>[,name=<guest-name>][,writable]
```

- `name` defaults to `.` — the name `preopens.get-directories()` reports to the guest.
- Mounts are read-only unless `writable` (or `writable=true`) is present.
- A bare token is shorthand for the path: `--mount workspace` and `--mount workspace,writable` are valid.
- CLI mount paths resolve against the current working directory; manifest mount paths resolve against the manifest's directory.

### Examples

```bash
# Single guest, zero config
<runtime> run ./target/wasm32-wasip3/debug/examples/http_wasm.wasm

# Manifest-driven deployment
<runtime> run --manifest deploy/omnia.toml

# Compiled-in default manifest (runtime! `manifest:` field or inline manifest keys)
<runtime> run

# Command mode with guest argv
<runtime> run ./cli_wasm.wasm -- greet Ada

# Writable workspace mount
<runtime> run ./agent_wasm.wasm --mount path=workspace,name=.,writable

# The guest sees HOME and every ORDERS_ variable
<runtime> run ./orders_wasm.wasm --env HOME --env 'ORDERS_*'
```

## `compile` (jit feature)

Ahead-of-time compile a `wasm32-wasip3` component to a serialized wasmtime component (`.bin`) for faster startup:

```bash
<runtime> compile <wasm> [-o <output>] [-t <triple>]
```

Without `-o`, the serialized component is written to **stdout** (redirect it: `<runtime> compile guest.wasm > guest.bin`). With `-o`, the value may be a file path (written exactly there, parent directories created) or an existing directory (the output lands inside it as `<input-stem>.bin`). `-t` names the target triple the artifact runs on (`aarch64-unknown-linux-gnu`, say) for cross-compiling; unset, the artifact is for the host. The subcommand compiles under the compile-affecting settings its own environment sets (`MAX_FUEL`, `MEMORY_RESERVATION`, …, read as `RuntimeOptions::load_env()?.compile_options()`), and the runtime that loads the artifact must run under the same ones, so run `compile` with the production values set. In code the settings are an explicit argument of the library call — `omnia::compile::compile(&wasm, output, target, &CompileOptions)` — where `CompileOptions::default()` matches a runtime whose environment sets none of them. That settings match is a compatibility check, not an authenticity check: a `.bin` is native code, and every path the CLI loads one from is a trusted operator input (see the [security model](../security-model.md)).

A runtime built without the default `jit` feature carries no compiler and refuses `compile`, naming the feature; pre-compile with a build of the same runtime that keeps it.

## Exit status (command mode)

- Guest `run()` returns `Ok(())` → exit 0.
- Guest `run()` returns `Err(())` → exit 1.
- Guest calls `wasi:cli/exit`'s `exit-with-code(n)` → exit `n`.

## Cargo features (`omnia` crate)

| Feature | Default | Effect                                                                                                                                                   |
| ------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jit`   | yes     | Cranelift JIT; run raw `.wasm` directly and enable `compile`. Disable to run only pre-compiled `.bin` components.                                         |
| `link`  | no      | Guest-to-guest dispatch (the `omnia-link` crate): every import a guest makes outside the runtime's own `wasi:`/`omnia:` namespaces is relayed to the guest exporting it. Without it such an import fails at boot. |
| `loader` | no     | The guest loader (`omnia:plugins/loader`) and the registry client a `source.package` guest is fetched with: assembly links the loader host and installs its grant — the deployment's guests as the names a `declared` load may name, its read-only mounts as the roots a `path` load reads through, of those the loading guest's grants reach, its `registries` as the routing a package is fetched by, and its `[plugins.grants]` as what a guest loaded by path or package runs under, within its loader's grants. A deployment declaring `registries` or a package guest requires it. |
