# CLI Reference

A runtime binary generated by `omnia::runtime!` accepts the `run` subcommand — unless it is a [direct command](runtime-macro.md#direct-commands-raw-argv-passthrough) (`mode: command` with a compiled-in deployment), which removes the host CLI entirely: such a binary has no `run` subcommand and no `--manifest`/`OMNIA_MANIFEST` override, and forwards its argv to the guest verbatim (`mybin greet Ada`, not `mybin run -- greet Ada`). Everything below describes the standard grammar, which ships in the `omnia-cli` crate and reaches a binary through the `omnia` facade's default `cli` feature. The `compile` subcommand is part of the library CLI (with the default `jit` feature) but requires a hand-written `main` to expose — the generated `main` handles `run` only.

## `run`

Run a single guest, or a manifest-driven deployment.

```bash
<runtime> run [WASM] [--manifest <omnia.toml>] [--mount <spec>]... [-- <guest args>...]
```

| Argument / flag         | Meaning                                                                                                                                                                          |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WASM`                  | Path to a guest — a standard WASI component (`.wasm`) or a pre-compiled component (`.bin`). Optional when a manifest is available via `--manifest`, `OMNIA_MANIFEST`, or the binary's compiled-in default. |
| `-m, --manifest <path>` | Deployment manifest (`omnia.toml`) for multi-guest deployments. Falls back to the `OMNIA_MANIFEST` environment variable, then to a default manifest compiled in via the `runtime!` macro's `manifest:` field or inline manifest keys (if declared). |
| `--mount <spec>`        | Preopen a host directory into the guest sandbox (repeatable). Layered over the manifest's `[[mount]]` entries; a matching guest-visible name overrides the manifest (last wins). |
| `-- <args>...`        | Everything after `--` is forwarded to the guest as its argv (command mode). `args[0]` is the program name, supplied by the runtime.                                              |

### Mount spec format

```text
path=<host-path>[,name=<guest-name>][,writable]
```

- `name` defaults to `.` — the name `preopens.get-directories()` reports to the guest.
- Mounts are read-only unless `writable` (or `writable=true`) is present.
- A bare token is shorthand for the path: `--mount workspace` and `--mount workspace,writable` are valid.
- CLI mount paths resolve against the current working directory; manifest mount paths resolve against the manifest's directory.

### Examples

```bash
# Single guest, zero config
<runtime> run ./target/wasm32-wasip2/debug/examples/http_wasm.wasm

# Manifest-driven deployment
<runtime> run --manifest deploy/omnia.toml

# Compiled-in default manifest (runtime! `manifest:` field or inline manifest keys)
<runtime> run

# Command mode with guest argv
<runtime> run ./cli_wasm.wasm -- greet Ada

# Writable workspace mount
<runtime> run ./agent_wasm.wasm --mount path=workspace,name=.,writable
```

## `compile` (jit feature)

Ahead-of-time compile a `wasm32-wasip2` component to a serialized wasmtime component (`.bin`) for faster startup:

```bash
<runtime> compile <wasm> [-o <output>] [-t <triple>]
```

Without `-o`, the serialized component is written to **stdout** (redirect it: `<runtime> compile guest.wasm > guest.bin`). With `-o`, the value may be a file path (written exactly there, parent directories created) or an existing directory (the output lands inside it as `<input-stem>.bin`). `-t` names the target triple the artifact runs on (`aarch64-unknown-linux-gnu`, say) for cross-compiling; unset, the artifact is for the host. The compile-affecting settings are an explicit argument of the library call — `omnia::compile::compile(&wasm, output, target, &CompileOptions)` — and the runtime that loads the artifact must run under the same ones: `CompileOptions::default()` matches a runtime whose environment sets none of them, and `RuntimeOptions::load_env()?.compile_options()` matches the environment the compile runs in. That settings match is a compatibility check, not an authenticity check: a `.bin` is native code, and every path the CLI loads one from is a trusted operator input (see the [security model](../security-model.md)).

The generated `runtime!` `main` does not dispatch `compile`; call `omnia::compile::compile` from a custom `main` to expose it.

## Exit status (command mode)

- Guest `run()` returns `Ok(())` → exit 0.
- Guest `run()` returns `Err(())` → exit 1.
- Guest calls `wasi:cli/exit`'s `exit-with-code(n)` → exit `n`.

## Cargo features (`omnia` crate)

| Feature | Default | Effect                                                                                                                                                   |
| ------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cli`   | yes     | The `run` grammar (via the `omnia-cli` crate) and `omnia::Cli`/`Command`/`Parser`. Without it a binary must be a direct command; no `clap` is linked.     |
| `jit`   | yes     | Cranelift JIT; run raw `.wasm` directly and enable `compile`. Disable to run only pre-compiled `.bin` components.                                         |
| `link`  | no      | Guest-to-guest dispatch (the `omnia-link` crate): every import a guest makes outside the runtime's own `wasi:`/`omnia:` namespaces is relayed to the guest exporting it. Without it such an import fails at boot. |
| `loader` | no     | The guest loader (`omnia:plugins/loader`): assembly links its host and installs the manifest's `on_demand` guests as the table a `load(name)` may name, package sources routed by `registries`. A deployment declaring `registries` requires it. |
| `mpk`   | no      | Memory protection keys in the pooling allocator (Linux x86-64).                                                                                          |
| `gc`    | no      | WebAssembly GC support and pooling GC-heap limits.                                                                                                       |
