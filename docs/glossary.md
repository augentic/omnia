# Glossary

Shared vocabulary for Omnia, Specify, and the `omnia-backends` repo. Older docs and comments used **floor** for the runtime platform; that term is retired here in favor of the entries below.

## Core vocabulary

### Guest

Application code compiled to a WebAssembly component (`.wasm`), targeting `wasm32-wasip3`. A guest talks only to WASI interfaces; it never names an implementation.

### Host

The native binary that loads guests and provides their capabilities. Usually generated by the `runtime!` macro; also "host runtime". A **WASI host** (e.g. `WasiKeyValue`) is one interface implementation linked into it.

### Backend

The implementation a WASI host delegates to — an in-tree default (`KeyValueDefault`, in-memory) or a production client from `omnia-backends` (`omnia_redis::Client`). Backends implement `omnia::Connect` and configure themselves from environment variables at startup.

### WIT

The [WebAssembly Interface Types](https://component-model.bytecodealliance.org/design/wit.html) definition language. Each interface crate's `wit/` directory holds the contract both guest bindings and host implementations are generated from.

### Trigger

A WASI host that runs a server and drives guest instances per inbound request: `WasiHttp`, `WasiMessaging`, `WasiWebSocket`. All other hosts only serve guest-initiated calls.

### Deployment manifest

The `omnia.toml` file (or equivalent programmatic `omnia::Manifest`) declaring guests and their [grants](#grants), mounts, routes, and the package store and registries. See [Configuration](reference/configuration.md#deployment-manifest-omniatoml).

### Guest entry

One guest a deployment declares: a `[[guest]]` table, a `runtime!` `guests:` entry, or an `omnia::GuestEntry`. Its `name` is the guest's identity (`GuestId`) — what routes and link dispatch address, and what a `load("name")` answers with; omitted, the component file's stem names it (`echo.wasm` is `echo`) or the package reference without its version does (`acme:tool@1.2.3` is `acme:tool`). A manifest file's entry reads its component from a file (`source.path`) or fetches a package (`source.package`); the macro's embeds it (`path:`) or names a package (`package:`). Embedded bytes load at boot; every other entry is a [first-use guest](#first-use-guest). An entry's optional [grants](#grants) narrow what its guest reaches.

### Grants

A ceiling one party sets on what another may reach. Omnia sets one at two levels:

- **Per guest**, a deployment's `omnia::Grants`: a manifest's `[guest.grants]`, the macro's `grants:`, or `GuestEntry::grants`. Its lists narrow the deployment for one guest:
  - `env`, the inherited host variables the guest sees;
  - `mounts`, the [mounts](#mount) preopened into it, and the ones a path it loads may lie beneath;
  - `hosts`, the host names its outbound `wasi:http` requests, its model workers' egress, and the registries it names to the [guest loader](#guest-loader) may reach;
  - `guests`, the guests it may call over a link or load through the [guest loader](#guest-loader), by name;
  - `interfaces`, the packages it may import code from, checked when it is admitted.

  A guest without grants reaches everything, and startup logs it. With them, an omitted list grants nothing. A guest the [guest loader](#guest-loader) admits by path or release runs under the deployment's `[plugins.grants]` within the grants of the guest that loaded it. See the [security model](security-model.md#per-guest-grants).
- **Per completion**, the `omnia:model` `grants` a guest lends one completion: a workspace beneath its own preopens, and the `worker-grant` bounding what the backend's worker reaches beyond it. See the [model reference](reference/model.md#grants).

### Registry

The runtime's map from each opaque guest identity (`GuestId`) to a pre-instantiated guest, plus the route tables, mounts, and link seam that hang off it. Per-request instantiation pulls from here.

### Mount

A host directory preopened into every guest sandbox its [grants](#grants) reach (`[[mount]]` in the manifest, the macro's `mounts:` list, or `--mount` on the CLI). Read-only unless marked writable; the guest sees it under its guest-visible name via `wasi:filesystem` preopens. A read-only mount is also a root the [guest loader](#guest-loader) reads a component from when a guest whose grants reach it names a path beneath it; a writable mount never is, and one that shares or nests a read-only mount's directory is refused at startup. Mounts dedup by name, last wins, before any directory opens — how a test overlays a binary's `.` root.

### Dispatch (host-mediated)

Guest-to-guest calls carried through the host: a guest imports an interface outside the runtime's own namespaces, and the host routes the call to whichever guest exports it. Nothing declares the seam — the [namespace rule](#namespace-rule) decides what crosses. A caller under [grants](#grants) reaches only the guests its `guests` list names. Nesting is bounded by `MAX_DISPATCH_DEPTH`. Distinct from the host→guest `Dispatcher`, which names its target explicitly. Both paths drive a fresh callee through `call_fresh`.

### Namespace rule

How the runtime tells its own interfaces from the ones guests share: an import or export under `wasi:` or `omnia:` is the host's (WASI, and omnia's capability hosts such as `omnia:plugins/loader`); every other interface crosses between guests — the host polyfills the import on the caller and serves the export on whichever guest carries it. `omnia::is_host(interface)` is the predicate. A guest's own package (`example:link/echo`, `emery:adapter/source`) therefore never collides with the host's. An import no guest exports is relayed too, so the deployment boots and the call fails.

### Link seam

The `LinkSeam` trait the registry drives for guest-to-guest dispatch: polyfill every guest import the [namespace rule](#namespace-rule) leaves to guests, serve the matching exports, refuse a guest that disagrees with a registered one on a linked function's signature, and publish or discard endpoints as guests enter and leave. A runtime built without the [`link` feature](#link-feature) installs `NoLinks` (every method a no-op); one built with it installs `InProcessLinks` from `omnia-link`. Endpoints move through two stages — `serve` parks pending state outside the registry's lifecycle gate; `publish`/`discard`/`remove` run under the gate — and a call never reads pending state.

### Link feature

Omnia's off-by-default `link` cargo feature: guest-to-guest dispatch via the `omnia-link` crate. Independent of the [`loader` feature](#loader-feature) — compiled-in guests may call each other; loaded guests may be host-only. Without it, an import outside the runtime's namespaces is unresolved and the deployment fails at boot.

### Loader feature

Omnia's off-by-default `loader` cargo feature: the [guest loader](#guest-loader) (`omnia-plugin`) and the registry client a `source.package` guest is fetched with. Independent of the [`link` feature](#link-feature). With it, `Deployment::assemble` links the loader host and hands the runtime its registry client for package sources; a deployment declaring `plugins` or a package guest is refused at startup without it.

### Guest loader

The `omnia:plugins` host capability: a guest names a source — `declared(name)`, one of the deployment's guests; `path(p)`, a component beneath one of its read-only [mounts](#mount); `release(reference, registry?)`, an exact package release — and the host acquires the bytes inside the deployment's grant (its guest list, the mounts the loading guest's [grants](#grants) reach, its package store, its `registries` routing) and admits them through the runtime's one admission body (`Runtime::admit_bytes`), which verifies them against the digest and seats them under the name the source derives (the declared name, the file stem, the reference without its version), returning a typed handle carrying the name, the content digest, and the names the component exports. A guest loaded by path or release runs under the deployment's `[plugins.grants]` within the loading guest's grants. A `declared` name is one more first use of the runtime's guest seam, so a [first-use guest](#first-use-guest) loads there exactly as a route would load it, under its own entry's grants, and one already active is attested. A path or release whose name is active under the same bytes and grants is attested too. A failed load answers one case: `not-found` for an undeclared name, a missing file, or a release nothing routes or holds; `denied` for a path beneath a writable mount or a mount the loading guest's grants do not reach, a name the deployment declares, a name active under other grants, or a component importing a package its grants do not reach; `invalid` for a malformed request or bytes that miss the deployment's pin; `unsupported`, `unavailable`, or `other`. Bytes that miss the load's own digest, or a name active under other bytes, answer a `conflict` instead. Component bytes never cross the interface, and the requester gains no lifecycle authority. Ships behind omnia's `loader` feature; linked at assembly for every deployment alike, reachable only from worlds that import it. The requester surface, `plugins::load` over the generated `Source`, `Plugin`, and `Conflict` records, ships in `omnia-sdk`'s `plugins` module.

### Package store

The directory a deployment's `plugins.store` names (the macro's `plugins: { store: .. }`, a manifest's `[plugins] store`): every package the runtime acquires is kept there, flat, one file per release named `namespace_name@version.wasm`. The `RegistryClient` reads it before any registry, so a release it holds is served with no network, whoever wrote it — the client after a fetch, `wkg get` into the directory, a plain `cp` — and a release is written once and never replaced: removing the file is the refresh. Only that spelling is a stored release. The store is where loaded code comes from, so it may not lie beneath a writable [mount](#mount), present or not. Omnia's `FsStore` is the local store; `PackageStore` is the trait an embedder's remote store implements (`omnia-azure-blob`'s container, say), and `NoStore` keeps nothing.

### First-use guest

A [guest entry](#guest-entry) whose component is not compiled into the runtime — every `[[guest]]` in a manifest file, and the macro's `package:` entries — and so loads the first time something names it: a route matching an event, the command drive (`command = true`), a link call, a host dispatch, or a `loader.load(declared(name))`. Nothing marks it; the source kind is the rule, and the retired `on_demand` key is refused. Its `source.path` is read at that first use, so `omnia compile` output loads from it only under a `digest` pin; its `source.package` is acquired by the `RegistryClient` over the deployment's [package store](#package-store) — served from the store when it holds the release, else fetched through the `registries` configuration (package override, namespace, then `default_registry`; a package routed nowhere is refused naming its namespace and the store) and written to the store once — or by the custom `RegistrySource` an embedder selected with `Deployment::registry_source`, and admits raw wasm alone. A first-use guest is never the catch-all a trigger falls back to; it takes routes and the command mark like any other. The seam every first use goes through is `Runtime::guest`.

## Guest SDK (`omnia-sdk`)

### Bindings

The guest side of each `omnia:*` interface: the Rust `wit-bindgen` generates from its WIT, committed under `crates/sdk/src/bindings` and re-exported by the `omnia-sdk` interface modules (`keyvalue`, `sql`, ...) with typed helpers beside the generated methods. `mise run bindgen` regenerates them, and CI fails when the committed bindings drift from the WIT.

### Handler contract

The transport-neutral unit of guest application logic: an `async fn(I) -> Result<O, E>`, or an `async fn(Context, I) -> Result<O, E>` when it reads the invocation's metadata, registered on a `Handlers` and invoked by the closed `Router`'s dispatch. The messaging router and the command façade are adapters that decode a transport event into `I` and encode the result back, as a request's reply on a request route; an HTTP route is a plain axum handler that may take the same `Context` as an extractor. A handler reaches the host through the [bindings](#bindings), and a test runs it as the compiled component. See [Writing Guests](guides/writing-guests.md#the-handler-contract).

### Provider

What serves one `omnia:*` interface to a guest: the [WASI host](#host) for the interface and the [backend](#backend) it runs over. A guest never names one; the deployment decides what backs each interface. What any provider owes the application is the [Provider Contract](reference/provider-contract.md).

### Command façade

`omnia_sdk::command`, the command-line adapter over the handler contract: `Handlers::command(name, handler)` registers a subcommand beside a module's paths and topics, the closed `Router` `run`s argv (clap decode → handler → encode in the selected `command::Format`, the output's `command::Render` form as text) onto a `Response { stdout, stderr, exit }`, and `command::export!(command_router)` binds the router fn as the `wasi:cli/run` export, writing the channels at that boundary. `parse` and `Command::call` are the same pieces for a hand-written clap grammar. The clap-backed parts ship behind the `command` cargo feature. Distinct from the host-side **`omnia-cli`** crate, which is the `run` grammar of a host binary.

### Failure envelope

What a command reports on stderr when a verb fails: the `Failure` type wrapping an `omnia_sdk::Error` plus an optional remedy hint. As text, `error[<code>]: <message>` then `hint: <hint>`; as JSON, flat `{"error","message","exit-code","hint"?}`. Its `error` and `message` are the transport-neutral `ErrorBody` that `Error::into_response` also emits as a JSON body, so one discriminant identifies a failure over HTTP and over a shell.

### Exit map

The fixed mapping from an `omnia_sdk::Error`'s `ErrorKind` to a process exit status, `Error::exit_code()`: `BadRequest` 1, `NotFound` 2, `ServerError` 3, `BadGateway` 4, `Conflict` 5 — the exit-code twin of `Error::status()` (400 / 404 / 500 / 502 / 409). A clap usage error exits `USAGE_EXIT` (64, `EX_USAGE`) rather than clap's default 2, so exit 2 always means a `NotFound` envelope. A guest never chooses an exit code; the error class does.

## Runtime platform

### Runtime core

The domain-agnostic in-tree platform: the `omnia` composition root, the `omnia-core` live-runtime SDK a capability crate targets, WASI host crates (`wasi-*`), WIT contracts, guest registry, and host-mediated dispatch. It routes opaque identities and satisfies typed effects; it does not embed adapter names, workflow policy, vendor model ids, or other consumer-specific knowledge.

Same layer as **Layers 1 + 2 (composition root + live-runtime SDK + WASI interfaces)** in [Architecture.md](Architecture.md). In Specify this is also called the **Omnia runtime core**.

### Facade

The `omnia` crate, the **composition root** and an embedder's only omnia dependency: it owns deployment assembly and process lifecycle, composes the crates beneath it — `omnia-link` (guest-to-guest dispatch, behind the `link` feature), `omnia-plugin` (the guest loader, behind the `loader` feature), `omnia-cli` (the `run` and `compile` grammar, a leaf crate), and `omnia-compile` (the ahead-of-time compiler, a leaf crate whose Cranelift backend the `jit` feature turns on) — and re-exports the `omnia-core` live-runtime SDK and the `runtime!` macro under `omnia::…` paths.

### Runtime contract

The stable WIT boundary and host behavior guests depend on — what must stay generic under **Law 2**. Often used when contrasting with pluggable backends (“vendor detail, never part of the runtime contract”).

### Law 2

Specify’s invariant that domain-specific knowledge lives in backends, guests, and orchestration — never in the runtime core. Omnia stays generic; which model, filesystem backend, or adapter satisfies an interface is deployment configuration the runtime core never parses.

## Host-side model completion (`wasi-model`)

### Host-side

Work done inside Omnia host crates (validation, dispatch, workspace resolution) as opposed to backend-side logic in the `omnia-backends` repo (e.g. genai’s tool loop).

### Guest check

The `omnia:model` request flag (`check`) under which the backend offers each candidate answer to the guest before finishing, as a `check` call over the session. The guest's `ok` ends the completion; its `err(text)` is appended verbatim as the correction turn and the backend goes round again. The host validates nothing about the answer — `format` only steers the provider — so acceptance lives with the guest that knows the type. `omnia_sdk::model::Request::complete_checked` sets the flag and answers each call, and `Question<T>` runs the exchange for a typed answer.

### Host-injected tools

Workspace tools the host serves from `grants.workspace` under reserved names (`read`, `list`, `write`). Guests must not redeclare these names in a request's `tools`. Backends that advertise them (genai: `read`/`list`) execute them host-side through the `ToolHost`, never through the session.

## Other uses of “floor” (not the runtime platform)

These appear elsewhere in Augentic docs and code with a **different** meaning. Do not read them as “runtime core.”

| Term | Meaning | Example |
|------|---------|---------|
| **Baseline / floor, not ceiling** | Minimum guaranteed behavior; implementations may do more | Declarative HTTP route table is the baseline; programmatic routing is allowed |
| **Compatibility floor** | Minimum CLI or tool version required | `project.yaml` `specify_version`, adapter `requires_specify` in `specify-cli` |
| **Minimum cap / floor** | Hard lower bound on a spec limit, not a target to hit | Skill line caps, ignore-directive rationale length |

When in doubt: if the sentence is about **Omnia hosting guests**, use **runtime core**. If it is about **versions or numeric limits**, use **minimum** or **compatibility floor**.
